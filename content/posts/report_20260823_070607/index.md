## 1. 需求理解与拆解

用户的核心需求是**“意图模型训练数据集怎么设计”**。结合提供的上下文（家庭机器人意图识别、LLM微调场景），该需求并非简单的数据收集，而是针对**大语言模型（LLM）微调（Fine-tuning）**场景下的意图识别任务，构建高质量、结构化、可执行的训练数据。

具体拆解为以下四个维度：

1.  **场景定义**：明确是单轮对话还是多轮对话？是单一意图分类还是包含槽位填充（Slot Filling）/ 参数抽取？
    *   *背景暗示*：文档提到“家庭机器人”、“play_music()”，暗示需要输出结构化的动作或API调用参数，而不仅仅是分类标签。
2.  **数据规模与分布**：确定每类意图的最小样本量、类别均衡策略以及多意图/多轮数据的比例。
3.  **数据格式规范**：定义输入（Instruction/Prompt）与输出（Output/Completion）的标准JSON结构，确保符合微调框架（如PAI、LLaMA-Factory等）的要求。
4.  **数据增强与质量**：如何覆盖丰富的问法（Paraphrasing）、处理噪声、以及构建负样本（Unknown Intent）。

## 2. 技术可行性分析

基于阿里云PAI、NVIDIA及AWS的最佳实践，意图数据集的设计在技术上具有高度可行性，且已形成标准化流程：

### 2.1 数据构建策略可行
*   **单意图基线**：每类意图 50-100 条样本即可作为微调基线。对于家庭机器人这类垂直领域，意图数量通常有限（如：开灯、调温、播放音乐、查询天气、闲聊、未知），总量可控。
*   **多轮/多意图增强**：多轮对话数据量建议为单轮的 20% 以上。这符合实际交互逻辑，即用户往往通过多轮澄清（“我想听音乐” -> “爵士乐”）来完成指令。
*   **自动化标注辅助**：利用 iTAG 或 LLM-as-a-Judge 进行半自动标注和清洗，可大幅提升数据生产效率。

### 2.2 格式标准化可行
*   **JSON 指令微调格式**：当前主流 LLM 微调均采用 `{"instruction": "...", "output": "..."}` 或 Chat 格式（`[{"role": "user", "content": "..."}, {"role": "assistant", "content": "..."}]`）。
*   **结构化输出约束**：通过 Few-shot Prompting 或 Constrained Decoding 训练模型输出严格的 JSON 格式（如 `{"intent": "play_music", "params": {"genre": "jazz"}}`），技术成熟度高。

### 2.3 数据增强手段可行
*   **LLM 合成数据**：使用通用大模型（如 Qwen, Llama 3）生成多样化的用户问法（“把灯打开”、“开启照明”、“亮一点”），有效解决长尾问法覆盖不足问题。
*   **负样本挖掘**：明确定义“未知意图”（Other/Reject）的数据比例，防止模型过度自信地错误分类。

## 3. 潜在风险点

| 风险类别 | 具体描述 | 潜在后果 |
| :--- | :--- | :--- |
| **数据偏差 (Bias)** | 某类高频意图（如“闲聊”）数据量过大，低频意图（如“紧急报警”）数据量过少。 | 模型对低频但高重要性的意图识别率极低；或模型倾向于将所有模糊输入分类为高频意图。 |
| **格式不一致** | 训练数据中 Output 字段有时是纯文本，有时是 JSON，有时包含额外解释性文字。 | 模型输出格式不稳定，后处理解析失败率高，导致业务逻辑执行错误。 |
| **多轮上下文丢失** | 多轮对话数据中，未正确保留历史上下文，或上下文与当前意图关联弱。 | 模型在多轮场景中无法正确指代消解（如“换个颜色”不知道是指灯光还是音乐封面）。 |
| **过拟合 (Overfitting)** | 样本量过少（<50/类）且缺乏多样性，模型死记硬背特定问法。 | 测试集准确率尚可，但生产环境中面对新问法时泛化能力差。 |
| **意图边界模糊** | 意图定义不清晰，例如“播放音乐”和“查询歌单”在用户表达上存在重叠。 | 模型在边界样本上预测波动大，需要频繁的人工干预或规则兜底。 |

## 4. 推荐技术方案

针对家庭机器人场景，推荐采用 **“分层构建 + 结构化输出 + 自动化增强”** 的数据集设计方案。

### 4.1 数据集结构设计

#### A. 意图体系定义 (Intent Taxonomy)
首先明确意图列表，建议分为：
1.  **设备控制类** (Control): `turn_on_light`, `set_temperature`, `play_music`
2.  **信息查询类** (Query): `query_weather`, `query_time`
3.  **闲聊/情感类** (Chat): `greeting`, `small_talk`
4.  **未知/拒绝类** (Unknown): `other` (用于兜底，防止幻觉)

#### B. 数据格式规范 (JSON Schema)
推荐采用 **Chat 格式** 以支持多轮，且 Output 严格为 **JSON 字符串**。

**单轮示例：**
```json
{
  "instruction": "把客厅的灯调暗一点",
  "output": "{\"intent\": \"set_light\", \"params\": {\"location\": \"living_room\", \"brightness\": \"lower\"}}"
}
```

**多轮示例 (关键：将历史对话拼入 Instruction 或采用 Chat 数组格式):**
*方案一：扁平化 Instruction (适合单轮微调模型)*
```json
{
  "instruction": "用户: 我想听音乐。\\n助手: 什么类型的音乐？\\n用户: 给我放个爵士乐吧。",
  "output": "{\"intent\": \"play_music\", \"params\": {\"genre\": \"jazz\"}}"
}
```
*方案二：Chat 数组格式 (推荐，更通用)*
```json
[
  {"role": "system", "content": "你是一个家庭机器人助手，请识别用户意图并抽取参数。"},
  {"role": "user", "content": "我想听音乐。"},
  {"role": "assistant", "content": "好的，请问您想听什么类型的音乐？"},
  {"role": "user", "content": "给我放个爵士乐吧。"},
  {"role": "assistant", "content": "{\"intent\": \"play_music\", \"params\": {\"genre\": \"jazz\"}}"}
]
```

### 4.2 数据构建流程

1.  **种子数据构建 (Seed Data)**
    *   由领域专家（机器人业务人员）为每个意图编写 5-10 条典型问法。
    *   确保包含标准问法、口语化问法、否定问法。
    *   *示例*：`turn_on_light` -> "开灯", "把灯打开", "亮一点", "别关灯"。

2.  **LLM 数据增强 (Data Augmentation)**
    *   使用 Prompt Engineering 调用通用 LLM 生成变体。
    *   **Prompt 示例**：
        > "你是一个数据增强专家。请针对意图 'set_temperature'，生成 50 条多样化的中文用户指令。要求：包含不同地点（卧室、客厅）、不同温度值（24度、暖和点、冷一点）、不同语气。输出 JSON 列表格式。"
    *   **过滤机制**：使用规则或另一个 LLM 检查生成数据的合理性（如温度是否在合理范围 16-30 度）。

3.  **多轮对话构建**
    *   基于单轮数据，模拟用户追问场景。
    *   场景：参数缺失（"放音乐" -> "什么音乐？"）、参数修正（"不对，是爵士乐"）。
    *   确保多轮数据中，最终意图在单轮数据集中已存在。

4.  **负样本与边界样本**
    *   增加 5%-10% 的 `other` 意图数据，包含：
        *   与机器人无关的问题（"今天股票怎么样？"）
        *   语义模糊无法判断的数据（"那个东西弄一下"）
        *   乱码或噪声数据。

5.  **数据清洗与去重**
    *   去除重复样本（使用 SimHash 或余弦相似度）。
    *   检查 JSON 格式合法性（必须能 `json.loads`）。
    *   检查标签一致性（相同语义的样本必须对应相同意图和参数结构）。

### 4.3 数据量建议 (针对家庭机器人)

| 数据类型 | 建议数量/类 | 总数据量估算 (假设10个意图) | 说明 |
| :--- | :--- | :--- | :--- |
| **单轮核心意图** | 100 - 200 条 | 1,000 - 2,000 条 | 覆盖主要问法，保证基线性能 |
| **多轮对话** | 20 - 50 条 | 200 - 500 条 | 提升上下文理解能力 |
| **未知/拒绝** | 50 - 100 条 | 500 - 1,000 条 | 防止过度拟合，提升鲁棒性 |
| **总计** | - | **~3,000 - 4,000 条** | 对于 7B-13B 模型微调，此规模通常足够收敛 |

### 4.4 评估指标设计

在训练前，需从数据集中划分出 **验证集 (Validation Set)** 和 **测试集 (Test Set)**，比例建议 8:1:1。

*   **意图识别准确率 (Intent Accuracy)**：`Correct Intents / Total Intents`
*   **槽位填充 F1-Score (Slot F1)**：针对参数抽取的精确率和召回率。
*   **格式合规率 (Format Validity)**：输出是否为合法 JSON 的比例。
*   **拒识率 (Rejection Rate)**：在测试集中，`other` 意图被正确识别为 `other` 的比例。

### 4.5 实施工具链

1.  **数据标注**：PAI-iTAG / Label Studio (人工校对 LLM 生成数据)
2.  **数据生成**：Python 脚本 + LLM API (Qwen/ChatGLM)
3.  **数据预处理**：Python (Pandas, JSON 解析)
4.  **训练框架**：PAI-DSW / LLaMA-Factory / Hugging Face Transformers
5.  **评估**：自定义 Python 脚本计算上述指标

通过上述设计，可以构建一个**结构清晰、分布均衡、格式标准**的意图模型训练数据集，有效支撑家庭机器人意图识别模型的高效微调与部署。
