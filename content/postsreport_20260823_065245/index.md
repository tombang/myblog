# 意图模型训练数据集设计技术洞察报告

## 1. 需求理解与拆解

**核心目标**：构建高质量、高覆盖度的意图识别训练数据集，用于微调（Fine-tuning）大语言模型（LLM）或小模型，使其能够准确识别用户指令的意图并提取关键参数。

**关键子需求拆解**：
1. **场景定义**：明确是单轮对话还是多轮对话，是单意图还是多意图识别。
2. **数据量规划**：确定每个意图类别的最小样本量及整体数据分布。
3. **数据格式标准化**：定义输入（Instruction）与输出（Output）的结构，包括意图标签和槽位（Slot）填充。
4. **多样性与覆盖度**：确保数据涵盖丰富的用户表达方式（问法）和边界场景。
5. **数据生成与标注流程**：确定是人工标注、LLM合成还是混合模式。

## 2. 技术可行性分析

基于阿里云PAI、NVIDIA NeMo及行业最佳实践，当前技术栈完全支持以下数据集设计策略：

### 2.1 数据规模策略
*   **单意图场景**：
    *   **基准线**：每个意图类别至少 **50-100条** 高质量标注数据。
    *   **均衡性**：各类意图数据量应保持均衡，避免长尾意图数据过少或头部意图数据过多导致模型偏置。
    *   **扩展性**：若微调效果不佳，优先增加数据量，尤其是针对错误率高的意图类别。
*   **多意图/多轮对话场景**：
    *   **比例要求**：多轮/多意图数据量建议占单意图数据的 **20%以上**。
    *   **依赖关系**：多轮对话中涉及的意图必须在单意图数据集中已经存在，确保模型先掌握基础意图再学习上下文依赖。
    *   **建议**：仅在单轮识别无法满足业务需求时，才引入多轮对话训练，因为多轮数据训练成本高且场景有限。

### 2.2 数据格式标准
采用 **JSON** 格式，包含 `instruction`（用户指令/上下文）和 `output`（意图标签+关键参数）两个核心字段。

*   **单轮示例**：
    ```json
    {
      "instruction": "我想听音乐。",
      "output": "play_music()"
    }
    ```
*   **多轮/参数抽取示例**：
    ```json
    {
      "instruction": "我想听音乐。给我放个爵士乐吧。",
      "output": "play_music(genre='jazz')"
    }
    ```
*   **复杂结构化输出（推荐用于参数丰富场景）**：
    ```json
    {
      "instruction": "静安柳营路附近的药店",
      "output": "{\"intent\": \"search_with_attribute\", \"address\": \"柳营路\", \"county_name\": \"静安区\", \"root_organization_type_name\": \"药店\"}"
    }
    ```

### 2.3 数据生成与增强策略
1.  **人工标注（iTAG平台）**：适用于小规模、高精度要求场景。通过PAI-iTAG等工具进行标准化标注，确保数据质量。
2.  **LLM合成数据**：
    *   **问法多样化**：利用LLM生成同一意图下的多种自然语言表达（如“放音乐”、“播放歌曲”、“来点音乐”）。
    *   **硬负样本（Hard Negatives）**：生成语义相近但意图不同的数据，提升模型对边界情况的区分能力（参考IEPile数据集策略）。
    *   **参数填充**：通过模板+LLM填充方式，自动生成包含不同槽位值（如时间、地点、类型）的数据。
3.  **混合模式**：以人工标注为核心种子数据，利用LLM进行数据增强和扩充，最后通过人工审核保证质量。

## 3. 潜在风险点

| 风险点 | 描述 | 影响 | 缓解措施 |
| :--- | :--- | :--- | :--- |
| **数据分布不均** | 某些高频意图数据过多，低频意图过少 | 模型对低频意图识别率低，整体性能失衡 | 严格监控各类意图数据比例，采用过采样/欠采样或加权损失函数 |
| **问法覆盖不足** | 数据中用户表达方式单一，缺乏口语化、模糊表达 | 模型在真实用户自然语言下泛化能力差 | 使用LLM生成多样化问法，加入口语化、省略句、错别字等噪声数据 |
| **参数抽取错误** | 输出格式不规范，参数缺失或错误 | 下游任务执行失败 | 严格定义输出Schema，增加参数校验规则，使用结构化JSON输出 |
| **多轮上下文丢失** | 多轮数据中关键信息分散在不同轮次 | 模型无法正确整合上下文信息 | 设计完整的对话历史作为Instruction，确保关键参数在上下文中可追溯 |
| **数据泄露/污染** | 训练数据与测试数据重叠，或包含基准测试数据 | 评估结果虚高，实际效果不佳 | 使用去污工具（如lmsys）过滤与公开基准相似的数据，严格划分训练/验证/测试集 |

## 4. 推荐技术方案

### 4.1 数据集设计架构

```
意图识别数据集
├── 1. 意图体系定义
│   ├── 意图列表（Intent List）
│   ├── 意图描述（Intent Description）
│   └── 槽位定义（Slot Schema）
├── 2. 数据生成
│   ├── 种子数据（人工标注，每意图≥50条）
│   ├── 数据增强（LLM生成多样化问法、参数填充）
│   └── 负样本构造（硬负样本、边界案例）
├── 3. 数据清洗与校验
│   ├── 格式校验（JSON Schema）
│   ├── 逻辑校验（参数与意图匹配性）
│   └── 去重与去污
├── 4. 数据划分
│   ├── 训练集（80%）
│   ├── 验证集（10%）
│   └── 测试集（10%）
└── 5. 数据格式
    └── JSON Lines (.jsonl)
```
